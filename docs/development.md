# 開発の手順

## 環境

Node.js 22（CI と同じ版）と npm を利用する。Windows では、vite のビルドと撮影を大文字のドライブ名のパス（`F:\…`）から実行する。小文字のドライブ名では html-proxy の処理が失敗する。

## コマンド

```bash
npm ci            # 依存パッケージのインストール（package-lock.json どおりに入れる）
npm run dev       # 開発サーバーの起動
npm run build     # ビルドと型の検査
npm test          # 試験（vitest run）
npm run verify    # 完了の条件（型・ESLint・全試験・JSON・言語ファイル・仕様との突き合わせ）
npm run smoke     # 全場面の撮影と、画面のエラーの検査
```

## 完了の条件

変更は、`npm run verify` に合格した時点で完了とする。画面に関わる変更は、`node scripts/shoot.mjs <場面>` で撮影し、画像で確認する。試験に合格しただけでは完了としない。見た目を保つ変更（部品への置き換えなど）は、変更の前後を撮影して比較する。見た目が変わる場合は、前後の画像を示して利用者の了承を得る。

## 進め方の原則

遊んだときの挙動、画面の内容、ターミナルの命令と出力、既存のセーブの読み込みといった外部仕様は、意図した変更以外では変えない。内部の構成を変えるときは、挙動の記録の試験（`src/__golden__`）と一致することで、外部仕様が保たれていることを確かめる。内部の構成の変更の途中で不具合を見つけても、同じコミットでは直さない。別の `fix:` のコミットで直し、挙動の記録を更新する。

決まりは、文書と注意だけに頼らず、ESLint の規則・試験・`check:*` の検査で破れないようにする。検査で守れない決まりは、なるべく作らない。

作る挙動は、依頼または教材で利用者が判断するものに限る。収束の過程・タイマー・再送のような時間の経過は作らず、結果だけを求める。操作の分かりにくさは、説明の文字を追加して補うのではなく、画面と仕組みを直して解消する。

想定外の入力は既定値で埋めず、例外で止める。ただし、セーブの移行だけは古いセーブを読めることを優先する。1つの短い関数のためだけにファイルを作らず、1つの話題としてまとまるときや、今後中身が増える見込みがあるときに別のファイルにする。

## 判断に迷ったとき

設計にない判断が必要になったときは、次の順で決める。

1. 同じ種類の箇所に既存の決定があれば、同じ規則を当てはめる。
2. 型や登録表に項目が不足していれば、元の定義（`src/data/schema.ts` の zod の型）にある項目をそのまま追加する。
3. データとスキーマが意図を示しているのにコードが読んでいない場合は、データの意図に合わせて直す。この修正は作業とは別の `fix:` のコミットにする。
4. それ以外の場合は、今の挙動（挙動の記録・既存の試験）を保つ方を選ぶ。

上の規則で決まらず、かつ外部仕様（遊んだ結果・セーブの形・画面の文言）が変わる場合に限り、作業を止めて利用者に確認する。

## 試験

試験は、シミュレーションの結果・依頼の合否・セーブの移行のように、壊れうる振る舞いを守るものだけを追加する。CSS やソースの文字列を正規表現で照合する試験、型の検査で保証される事を確かめる試験、渡した props がそのまま HTML や属性に出ることだけを確かめる試験は作成しない。こうした試験は、トークンと開発の時間を消費してファイルを増やすだけで、不具合を防がないためである。この方針はこれから追加する試験に当てはめ、既存の試験を洗い出して削除する作業は行わない。

依頼と教材については、用意された構成では不合格になり、正解の構成では合格になることを試験で確かめる。

作業中は、変更したファイルに対応する試験だけを実行する（`npx vitest run <ファイル> --reporter=dot`）。全体の確認は、コミットの前に `npm run verify` で1回行う。

## コミット

1つの作業を終えるごとにコミットする。`git add` はファイルを指定して行い、`git stash` は利用しない。コミットの前の hook（`.git/hooks/pre-commit`）は、ステージしたファイルの ESLint と JSON の重複キーを検査する。`--no-verify` は利用しない。

ソース・試験・コミットメッセージには、作業の管理用の番号や非公開の文書への参照を書かない。コメントには、「TTL はルーターを1台通るごとに1減る」のように規則の中身を書く。
