# 開発の手順

Node.js 22 と npm を利用する。Windows では、vite のビルドと撮影を大文字のドライブ名のパスから実行する。

```bash
npm ci                                    # 依存パッケージのインストール
npm run dev                               # 開発サーバーの起動
npm run verify                            # 型・ESLint・全試験・JSON・言語ファイル・仕様の検査
npx vitest run <ファイル> --reporter=dot   # 変更した箇所の試験だけを実行する
node scripts/shoot.mjs <場面>             # 画面を shots/ に撮影する
```

JSON は `scripts/json.mjs` で、言語ファイルは `scripts/lang.mjs` で編集する。手順は [AGENTS.md](../AGENTS.md) に書く。セーブの形を変える手順は[セーブデータ](save.md)に書く。撮影の場面は[開発用のツール](tools.md)に書く。

## 完了の条件

変更は、`npm run verify` に合格して完了とする。画面に関わる変更は、撮影して確認する。見た目が変わる場合は、前後の画像を示して了承を得る。

## 原則

外部仕様は、意図した変更のときだけ変える。外部仕様は、遊んだときの挙動・画面・ターミナルの出力・既存のセーブの読み込みを指す。内部の構成を変えるときは、挙動の記録の試験との一致で確かめる。途中で見つけた不具合は、別の `fix:` のコミットで直す。

決まりは、ESLint の規則・試験・検査で守らせる。

想定外の入力は例外で止める。セーブの移行だけは、古いセーブを読むことを優先する。

## 判断に迷ったとき

設計にない判断は、次の順で決める。

1. 同じ種類の箇所の既存の決定に合わせる。
2. 型や登録表の項目が足りない場合は、`src/data/schema.ts` の項目をそのまま追加する。
3. データの意図をコードが読んでいない場合は、データに合わせて別の `fix:` のコミットで直す。
4. どれにも当たらない場合は、今の挙動を保つ。

外部仕様が変わる判断は、作業を止めて利用者に確認する。

## 試験

試験は、壊れうる振る舞いを守るものだけを追加する。シミュレーションの結果・依頼の合否・セーブの移行が該当する。CSS やソースの文字列の照合、型で保証される事、props の素通しの試験は作らない。既存の試験の洗い出しと削除も行わない。

## コミット

作業を終えるごとにコミットする。`git add` はファイルを指定する。`git stash` と `--no-verify` は利用しない。ソースとコミットメッセージに、作業の番号と非公開の文書への参照を書かない。
