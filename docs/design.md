# 設計の方針

## 目指すゲーム

ほのぼのとしたドット絵の経営シミュレーションで、ネットワークを設計・構築するゲームを目指す。プレイヤーは小さな事務所から始め、会社を大きくし続ける。明確な終わりは設けず、目標の象徴を自社データセンターとする。

遊ぶ人は、ネットワークの初心者からネットワークスペシャリスト試験の受験生までを想定し、経営シミュレーションが好きな人も対象とする。最も大切にする体験は、設計して配線したネットワークがつながる瞬間であり、機器を並べてケーブルを挿していく組み上げの過程も重視する。面白さと学習の比重は段階で変え、序盤は手軽さを優先し、進むほど実際の設計に近い判断を求める。

設計はプレイヤーが行い、社員は施工を担う。PC のブラウザを主な環境とし、スマートフォンでも一通り遊べるようにする。失敗の厳しさはゆるめにし、疎通テストは何度でも実行でき、倒産はめったに起きないようにする。機器は汎用の架空製品とし、実在の製品名やメーカーを模したものは利用しない。社員や顧客には、笑える小ネタを持たせる。

## 遊びの作り方

新しい仕組みは、中心の体験に役立つ場合に限って追加する。新しい概念は1つずつ出し、失敗しても損のない場面で出してから、次の依頼で練習させ、その後に組み合わせる。

依頼と教材は対で作る。論点ごとに、学ぶための教材と、それを使う依頼を1つ以上用意し、教材と経営が別のゲームにならないようにする。修理の依頼の文面には症状だけを書き、原因は書かない。障害は乱数で起こさず、障害対応の依頼として扱う。

操作には、即座の反応、状態の見やすさ、取り消しの手段、目標の明示を備える。

## シミュレーションの範囲

作る挙動は、依頼または教材で利用者が判断するものに限る。収束の過程・タイマー・再送のような時間の経過は作らず、隣接できるか、どの経路が選ばれるかといった結果だけを求める。

挙動は現実のネットワークに合わせる。ゲームの都合で現実と異なる仕様にした箇所は、現実に合わせることが改善になる場合、変えてよい。

## 見た目

派手な光・ビーム・パーティクル・画面揺れは使わず、状態の変化は吹き出し・小さなアイコン・LED の明滅で表す。マップは斜め見下ろしのドット絵とし、手前の壁を取り除いた断面図として部屋を描く。拡大は整数倍に限り、補間しない。UI のアイコンと機器の背面の部品は、正面から見た平らな絵にする。強調色は、正常・警告・異常といった状態の表示だけに使う。

素材・キャラクター・UI はすべて本作のオリジナルとし、既存作品の画面構成や固有の演出は再現しない。

## UI の部品

画面の重なりを段階に分け、地の色を段階ごとに1つとする。色の値は `src/components/ui/tokens.css` に置く。

| 段階 | 役割 | トークン |
| --- | --- | --- |
| 床 | 地図とタイトルの背景 | `--bg-floor` |
| 窓 | 窓・確認の窓・ツールバー | `--bg-window` |
| 札 | 窓の中のカード・一覧の行・通常のボタン | `--bg-card` |
| 欄 | 入力欄・選択の欄・吹き出し | `--bg-field` |
| 窪み | ターミナルの出力と入力 | `--bg-well` |

ボタンの種類は役割で選ぶ。`primary` は、受注・採用・保存のように、その場の目的を進める操作に使う。1つの窓に1つまでとし、Enter で押すボタンと一致させる。`secondary` は、閉じる・戻る・購入のような通常の操作に使う。`danger` は、削除・辞退・作り直しのように失うものがある操作に使う。`outline` は、並んだ選択肢と取り消しに使う。押せないボタンは、部品の `disabled` で不透明度を下げて表す。

見た目の規則は、[コードの書き方](coding.md)の「画面の部品」に記載している。
